# S/4HANA 低版本适配规划（BASIS 7.50/7.51）

> 状态：规划稿（2026-10-07），待评审后开工。**2026-10-15 更新：目标版本真机
> 基线已取得——ED1 = S/4HANA 1610 SP2（S4CORE 101 / BASIS 751 SP2 / kernel 749 /
> HANA），证据 `docs/evidence/low-release-ed1-751-baseline.md`；§2 表中已标
> 【已核验】的行来自该真机取证，M1 可直接以 ED1 为验证目标。**
> 版本对照：S/4HANA 1511 = BASIS 7.50；1610 = BASIS 7.51（on-premise 最低两代）。
> 事实来源：abap-docs 特性矩阵（software-heroes ABAP Feature Matrix，7.40 SP02~2025 全列）、
> SAP Community 博客 community-14414381（ADT-over-RFC 实证）、本项目 ED1 真机经验
> （受控创建链 transportchecks 包 URI 映射缺陷已定性，降级路径已验证）。

## 1. 目标与范围

**本期目标**：让本项目（MCP v2 双栈，当前 0.9.0）在 S/4HANA 1511/1610（BASIS 7.50/7.51）上
以受控、可取证的方式提供与高版本一致的工具面（差异显式声明）。

**范围内**：
- 版本指纹探测 + 每工具最低版本能力矩阵 + 工具目录按版本自动裁剪/降级。
- 7.50/7.51 上缺失或降级能力的显式定性（隐藏、INTENTIONAL_RESTRICTION、降级路径三类）。
- 受控创建链在 7.51 的传输预检降级路径产品化（ED1 已验证的"指定传输号不预检 + corrNr"）。
- 真机（7.50/7.51 专用 DEV）证据战役，能力矩阵加 release 维度徽章。

**范围外（本期不做，但架构上预留）**：
- ECC / NW 7.31-（7.31 以下无 CDS、无内联声明、无 APC，工程性质不同，属下一期）。
- RAP 能力在低版本的替代实现（RAP 本身 7.55+ 才存在，无从替代，只能声明限制）。

**关键判断**：S/4 1511/1610 与现有支持版本同属现代 ABAP 栈——CDS、内联声明、APC、ATC、
AMDP 基础全都在 7.40 SP05+ 就位。**本期的主体工程是"能力协商"，不是"能力重建"**。
预估 71 能力中约 57~59 个可直接维持 EQUIVALENT，需隐藏/降级的点高度集中（见 §3）。

## 3. 71 能力盘面差距分析（初判）

- **直接维持 EQUIVALENT（预估 57~59）**：全部 RFC 域工具、ADT 基础读/写/受控链、
  CDS 分析主面、cluster_read、impact、git.abapgit、execute-abap、health、ATC 面等。
- **INTENTIONAL_RESTRICTION（1）**：`debug.amdp-adt`——ADT AMDP 调试资源 7.53 起。
- **版本隐藏（10~12）**：rapGenValidateInitial/rapGenGetSchema/rapGenGetContent/
  rapGenGetUiConfig/rapGenValidateContent/rapGenPreview/rapGenIsAvailable、
  previewRapOperation/applyRapOperation，以及受控创建链中 BDEF/SRVD 等 RAP 时代对象类型。
- **降级运行（2~3）**：受控传输预检（transportchecks 包 URI 缺陷 → 降级路径）；
  CDS metadata extension 子面（仅 7.50）；受控创建能力目录在 7.50/7.51 收窄后的计数逻辑。

> 精确数字以 M1 逐工具登记 minRelease 后为准；本节仅定盘面方向。

## 4. 里程碑计划

### M0 版本指纹与能力矩阵（数据层）——不需要新环境，可立即开工

1. 新增系统指纹探测：复用 RFC 通道读 `RFC_SYSTEM_INFO`（BASIS 75x）+ `CVERS`
   （S4CORE 100=1511 / 101=1610、SAP_ABA 750/751），输出结构化
   `sapRelease / s4core / basisRelease` 指纹；识别失败 fail-closed 按"未知版本"处理。
2. 新增每工具能力元数据：在工具注册处（`src/config/ToolProfiles.ts` 工具集合旁）
   声明 `minBasisRelease`（默认 750），仅对版本敏感工具显式登记。
3. 建立能力矩阵数据文件（`src/config/SapReleaseCapability.ts` 或等价物）+ 单测
   （对齐 `ToolCatalogIntegrity.test.ts` 基线风格）。

验收：指纹探测对 sap-demo（现版本）与 ED1（7.51）双真机输出正确；矩阵单测全绿。

### M1 工具目录版本裁剪（执行层）✅ 2026-10-16 完成并通过 ED1 外部真机端到端验收

1. 在 `ToolOperationPolicy.ts` 现有 systemRole 门控旁并列加 releaseGate：
   低于 minRelease 的工具 = 隐藏（目录不出现）+ dispatch 拒绝（双保留，沿用
   QAS/PRD 裁剪的现有实现模式）。
2. healthcheck / sapDoctor 输出 release 维度 capability report（含被裁剪工具清单与原因）。
3. 前端/agent 可感知：裁剪不静默——响应错误明确说明"当前 BASIS 7.51 不提供 X，原因 Y"。

验收：模拟 7.50/7.51 指纹时工具目录数量与预期一致；隐藏 + dispatch 拒绝双保留有测试覆盖；
高版本行为零变化（现有 2131 测试不回归）。

### M2 受控链 7.51 降级路径产品化 ✅ 2026-10-16 完成并通过 ED1 外部真机端到端验收（M2-B 核实为既有能力）

1. 受控创建/传输预检在 7.50/7.51 指纹下自动走"指定传输号不预检 + corrNr"
   （ED1 已验证路径），plan 状态机、漂移校验、确认模式（native/auto）不变。
2. 受控创建能力目录（31 类）按版本收窄：BDEF/SRVD 等 RAP 时代类型在 7.50/7.51
   从 `describeRepositoryObjectCreation` 清单中剔除并标注版本原因。
3. `check:repository-creation-coverage` 脚本支持 release 维度基线。

验收：7.51 真机上受控创建链端到端一次（创建→读回→清理→缺席复核）全通；
降级路径在 plan 审计中如实记录 `transportPrecheck=downported`。

### M3 WebSocket 桥 / git.abapgit 7.51 真机验证

1. 在 7.51 专用 DEV 部署 ZADT_VSP git service + abapGit（照搬 sap-dev 部署 playbook：
   DDLS 语法坑、激活收敛、SAPC/SICF 步骤清单）。
2. 真机跑通 gitTypes/gitExport 链路（APC WebSocket 7.50/7.51 协议差异逐项记录）。
3. 若 7.50（1511）无环境，WebSocket 面标注"7.51 实证 / 7.50 待验证"。

验收：git-bridge-real-dev-smoke 在 7.51 全通或差异留档。

### M4 真机证据战役 + release 维度徽章

1. 以 `sap-dev.env`（7.51）为基线环境，跑全套 real-dev smoke（读面/写面/受控链/
   cluster/impact/git-bridge），每份证据文件头部标注目标 release。
2. 能力矩阵（71 能力）更新为双列：high（现状）× low（7.50/7.51），成熟度徽章加
   `REAL_DEV_VERIFIED@751` 等标记；`docs/evidence/repository-creation-maturity-evidence.json`
   加 supportedReleases 字段。
3. §2 事实表中每个 ❌/⚠️ 逐条复核落档。

验收：矩阵双列发布-ready；所有"已验证"表述可追溯到 7.51 真机证据文件。

### M5 发布 0.10.0 + 文档

## 5. 依赖与前置条件

- **7.51 真机 DEV**：ED1 即 S/4 1610 SP2 企业 DEV 本尊（2026-10-15 确认，非代理），可直接开工 M1-M3；
  若有正式 1610 客户环境则 M4 补充取证。
- **7.50（1511）环境**：非阻塞项——按"7.51 实证 / 7.50 待验证"分级发布，不为其推迟整体。
- **版本识别准确性**：S4CORE/CVERS 在部分精简系统可能缺失，指纹退化到 BASIS 75x 也可用
  （裁剪矩阵按 BASIS 版本为主键设计，S/4 具体代次仅作展示信息）。
- **RFC 白名单**：M0 的 CVERS 读取走现有 readRfcTable 通道，无需新增 FM 授权。

## 6. 风险与红线

1. **能力矩阵维护成本**：minRelease 元数据若靠手工登记会漂移——M1 起以"默认 750、
   例外显式登记"的规则降低维护面，并纳入 ToolCatalogIntegrity 基线测试防漂移。
2. **降级路径的安全语义**：transportchecks 跳过不等于放宽红线——未释放/零对象/本人属主
   三条核验必须在 apply 前用读面证据补齐，否则拒绝；此点写入 M2 验收。
3. **ED1 证据分量（2026-10-15 修正）**：ED1 已确认为**企业 ERP DEV 真机**
   （erpdev1.dfdchem.com，S/4 1610 SP2，非 developer edition），结论分量高于
   developer edition；但仍为 DEV 非客户生产，发布表述按"1610 DEV 真机实证"处理。
4. **不连生产红线照旧**：所有取证仅专用 DEV；7.50/7.51 适配不引入任何生产连接。
5. **一个数据来源纪律**：本文 §2 的版本结论中，凡未标【已核验】的，
   发布物料中必须带"待验证"标记；【已核验@751】均须可追溯到
   `docs/evidence/low-release-ed1-751-baseline.md` 及后续 M4 证据。

## 7. 开工建议顺序

M0（数据层，无环境依赖）→ M1（裁剪层）可与 M3 部署准备并行 → M2 依赖 ED1 连通 →
M4 统一取证 → M5 发布。M0+M1 预估为纯本地工程（现有测试体系可完全验证），
M2-M4 各需一次 7.51 真机会话。
