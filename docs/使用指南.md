# abap-ai-workbench-mcp 使用指南

更新时间：2026-10-16。本文是安装、配置和安全操作入口；逐类创建证据与历史过程不在此复制。

## 1. 产品入口与版本

当前版本为 `0.10.0`，npm 包为 `abap-ai-workbench-mcp@0.10.0`（0.10.0 = S/4HANA 低版本适配：BASIS 7.50/7.51 版本能力协商 + RFC 72 字符兼容 + 受控创建 kind 收窄；0.9.x = MCP v2 双栈、能力收编批次 64/71 与受控导入三件套，详见 CHANGELOG）。新安装按角色选择：

| 入口 | 等价 profile | 工具数 | 适用角色 |
| --- | --- | ---: | --- |
| `focused` / `developer` | `development-workbench` | 185 | 开发人员 |
| `business` | `business-readonly` | 18 | 业务顾问 |
| `operations` | `operations-readonly` | 58 | 运维人员 |
| `expert` | `legacy-full` | 220 | 专家和旧脚本 |

`safe`、`development`、`diagnostic-readonly` 等旧名称继续兼容。完整定位见 [`产品定位.md`](产品定位.md)。

### MCP 协议兼容（0.9.0 起）

自 0.9.0 起服务器基于 MCP 官方 v2 SDK 双栈运行，同一进程同时服务两个协议世代：

| 客户端 | 连接方式 | 说明 |
| --- | --- | --- |
| 2026 世代（如 ZCode 新版 auto 协商） | `server/discover` 探测 | 原生 2026-07-28 协议，秒级握手，无需任何客户端配置 |
| 2025 世代（v1 SDK 宿主、多数现网工具） | `initialize` 握手 | 行为与 0.8.x 完全一致 |

受控写入的原生确认（preview→apply 的表单确认）在两个世代下语义一致：2025 连接
走服务器→客户端确认请求；2026 连接走 input_required 多轮确认，由 v2 SDK 的
legacy shim 保证旧客户端零感知。

> 0.8.x 及更早版本在 ZCode 0.16.9+ 的 auto 协商下会因探测超时导致连接耗时
> 15~19 秒、工具注册不完整。若仍运行旧版，可在该服务器条目加
> `"protocolVersion": "legacy"` 规避；升级 0.9.0 后可移除该配置恢复 auto。

## 2. 前置条件

- Node.js 22.14+、npm，以及可通过 ADT 访问的 SAP ABAP 系统（Node 18/20 已
  EOL，自 0.7.0 起不再支持；Windows 可用 nvm-windows 按仓库 `.nvmrc` 切换）。
- SAP 已启用 `/sap/bc/adt`，用户具备目标操作所需权限。
- 写操作使用允许的命名空间、可传输包和已有未释放传输请求。
- QAS、PRD、缺失和未知系统角色始终只读。

## 3. 安装与配置

### npm（推荐）

```powershell
npx -y abap-ai-workbench-mcp@0.10.0
```

### 源码

```powershell
npm install
npm run build
node dist/index.js
```

将 `.env.example` 复制到仓库外的私有路径，通过 `SAP_MCP_ENV_FILE` 指定。至少配置：

```env
SAP_URL=https://your-sap-server.example:44300
SAP_USER=YOUR_SAP_USERNAME
SAP_PASSWORD=YOUR_SAP_PASSWORD
SAP_CLIENT=100
SAP_MCP_TOOL_PROFILE=focused
SAP_MCP_SYSTEM_ROLE=DEV
SAP_MCP_ALLOWED_HOSTS=your-sap-server.example
SAP_MCP_ALLOWED_CLIENTS=100
SAP_MCP_ALLOWED_NAMESPACES=Z,Y
SAP_MCP_AUDIT_PATH=D:\sap-mcp-audit
```

生产环境可使用 `SAP_MCP_CREDENTIAL_COMMAND` / `SAP_MCP_CREDENTIAL_TARGET`，避免把密码写入环境文件。不要提交 `.env` 或凭据。

常用护栏：`SAP_MCP_MAX_CONCURRENT_TOOLS=1`（写槽：stateful 写链/受控 apply 串行）、`SAP_MCP_MAX_READ_CONCURRENT_TOOLS=2`（读槽：read-only 工具在读域 stateless 会话上并发，范围 1–8）、`SAP_MCP_ADT_TIMEOUT_MS=60000`、`SAP_MCP_QUERY_MAX_ROWS=5000`、`SAP_MCP_SEARCH_MAX_RESULTS=500`、`SAP_MCP_MAX_ARGUMENT_BYTES=5242880`、`SAP_MCP_MAX_RESPONSE_BYTES=10485760`。所有变量的范围见 `.env.example`。

较旧的 S/4HANA 目标（BASIS 7.50/7.51，即 S/4HANA 1511/1610）自 0.10.0 起自动做版本能力协商：启动时懒探测 RFC 指纹并隐藏目标版本不支持的工具（RAP 生成面、AMDP 调试 kind 等），行为对现代版本零影响。若探测失败（如网关不可达），可设 `SAP_MCP_BASIS_RELEASE` 显式指定 BASIS 版本号；未解析时门控保持关闭（fail-closed，不猜测）。

### 3.1 客户端工具超时配置（重要）

部分 MCP 客户端（如 ZCode）默认工具超时仅 30 秒，且**超时后会杀掉 stdio server 进程**——对本服务是灾难性行为：plan store 丢失（旧 plan 全部 `PLAN_NOT_FOUND`）、进行中的 apply 被腰斩（SAP 端可能继续执行而客户端已失联）、SAP 锁残留（等待 30–60 分钟自动回收或手工 SM12 处理）。受控创建链/激活/确认 apply 在慢系统上经常超过 30 秒，务必按以下方式放宽：

```json
// ZCode 客户端 config.json（示例：放宽到 10 分钟）
{
  "mcp": {
    "servers": [
      {
        "name": "abap-ai-workbench",
        "command": "node",
        "args": ["D:/path/to/abap-ai-workbench-mcp/dist/index.js"],
        "timeoutMs": 600000
      }
    ]
  }
}
```

注意事项：

1. **字段名必须是 `timeoutMs`（数字毫秒）**；写成 `timeout` 无效。
2. **修改配置后必须重启 MCP 客户端**（整个客户端应用，不只是杀 server 进程）——客户端仅在启动时读取该配置，仅重启 server 进程不会重新加载。
3. 建议值不低于 `120000`（2 分钟）；开启 `SAP_MCP_CONFIRMATION_MODE=native` 人工确认的场景建议 `600000`（10 分钟），确认等待时间计入工具超时。
4. 判断服务端被杀的特征：工具报超时后，再次调用报旧 plan `PLAN_NOT_FOUND` 且 healthcheck 出现新 session——此时用新 plan 重做，不要重放旧 plan。
5. 已知问题反馈方向（客户端团队）：超时后应仅放弃等待而不应杀掉 stdio server 进程；同时支持 `MCP_TIMEOUT` / `MCP_TOOL_TIMEOUT` 环境变量。

二次确认模式 `SAP_MCP_CONFIRMATION_MODE`（默认 `native`）：`native` 下所有受控 apply 都需要一次人工原生确认；`auto` 为部署级预授权——apply 一次调用直接执行，AI 可全权完成受控写入。`auto` 仅允许 `SAP_MCP_SYSTEM_ROLE=DEV`，其他角色启动即报错（fail-closed）；该开关只由部署环境变量控制，调用方没有任何参数可以触发跳过确认。auto 模式下审计记录 `confirmationMode=auto-config`，preview plan 状态机与漂移校验保持不变，当前模式可通过 healthcheck 的 `confirmationMode` 字段核验。

## 4. 工具与安全流程

### 4.1 五分钟上手

新安装使用 `focused`（开发）入口时，推荐按下面顺序调用：

1. `sapDoctor`：一次检查本地配置和 SAP ADT capability；出现 `CHECK_REQUIRED` 时先按 `nextSteps` 修复。
2. `sap`，`action=help`：查看任务动作和参数示例。
3. `sap`，`action=read`：读取一个完整对象，例如 `params={"objectType":"CLASS","objectName":"ZCL_EXAMPLE"}`。
4. `sap`，`action=search` 或 `action=diagnose`：搜索对象，或从系统能力/运行 Dump 开始排查。
5. 需要修改或创建时使用 `sap` 的 `action=edit` / `action=create` 生成预览；真正应用仍使用服务端返回的 plan ID 和原有确认流程。

`sap` 是任务分流入口，不会创造新的 SAP 写入协议；每个动作最终仍调用现有工具，因此旧工具和旧脚本可以继续使用。`sapDoctor` 只读，不会创建、修改、激活或删除 SAP 对象。

源码修改必须依次执行：

1. `inspectAbapObject` 读取完整源码和元数据。
2. `previewAbapChange` 生成完整 diff 与服务器计划。
3. 审阅 diff，直接用 `changePlanId` 调用 `applyAbapChange`。
4. 用 `getAbapChangeStatus` 检查语法、激活、哈希和解锁。

仓库对象创建使用 `list/describe/preview/apply/status` 五个受控工具；cleanup 是独立的三工具流程，在 DEV workbench 中开放，并由 `SAP_MCP_ALLOWED_NAMESPACES` 与传输归属校验约束。所有 apply 都由服务端发起一次原生确认，不接受调用方确认布尔值、任意 URL、XML/JSON、媒体类型或 lock handle。唯一例外是 `SAP_MCP_CONFIRMATION_MODE=auto`（默认 `native`，仅 DEV 可配置）：人工确认由部署配置预授权替代，apply 一次调用直接执行，审计如实记 `confirmationMode=auto-config`；plan 状态机、漂移校验与 audit 链保持不变。

传输请求创建（仅创建一个动作）使用 `previewTransportCreation` / `applyTransportCreation` / `getTransportCreationStatus` 三工具受控链：preview 对目标包做只读 CTS 预检并冻结 plan（锚点 URI 由服务端从包名推导，不接受任意 URL），apply 经一次原生确认后单次创建工作台请求并用 `transportDetails` 读回验证请求号；释放、改属主与直改 E071/E071K 不在本链路面。创建异常、返回号为空或读回不一致时 plan 置 `UNKNOWN_OUTCOME` 并停止——请求可能已创建，先只读核验再决定下一步，绝不自动重试或自动删除。空请求的删除由独立的清理三件套 `previewTransportCleanup` / `applyTransportCleanup` / `getTransportCleanupStatus` 承担：preview 只读核验三条红线（未释放状态 D + 零对象 + 本人属主，任一不满足即拒），apply 经一次原生确认后单次删除并验证请求缺席；非空、已释放或他人属主的请求仍然不可删。

远端结果不明确、锁状态不明确或源码漂移时立即停止；先只读核验，再用新 plan。历史 `OUTCOME_UNKNOWN`、`COMPENSATED` 和 `COMPENSATION_FAILED` 计划不可重放。

## 6. 重启与验证

修改源码、配置或 `dist` 后完整重启 MCP 客户端。新 session 应能通过 `healthcheck` 识别正确的 host/client/profile；旧 plan 应返回 `PLAN_NOT_FOUND`。

本地门禁：

```powershell
npm test -- --runInBand
npm run build
npm run check:repository-creation-coverage
git diff --check
```

构建后可运行 `npm run test:focused-entrypoint` 做本地 MCP stdio 冒烟。该测试只验证 `initialize`、`tools/list` 和 `sap(action=help)`，使用虚拟 SAP 地址，不访问真实 SAP。

在明确授权的 DEV 环境中，可运行 `npm run test:focused-real-dev:readonly -- "C:\\path\\to\\sap-dev.env"` 验证 `sapDoctor`、`sap(read)`、`sap(search)` 和 `sap(diagnose)`。该脚本只读，不输出源码、业务行或凭据。

源码预览可运行 `npm run test:focused-real-dev:preview -- "C:\\path\\to\\sap-dev.env" ZCODEX_MCP_TEST S4HK900009`。脚本先读取完整源码，再追加一行注释生成 preview，验证语法、传输、diff 和 `PREVIEWED` 计划；它不会调用 apply，不会锁定、写入或激活对象。预览计划会随 MCP 进程结束而失效。

当前源码自动化基线（2026-09-25）：169 个 Jest suites、1776 个 tests（全量与默认覆盖率门禁通过）。真实 SAP smoke 只在明确授权和专用 DEV 配置下运行（默认 `sap-demo.env`）；组合链与目录层工具已于 2026-09-24/25 在专用 DEV 上真机验证（见 6.2/6.3/6.4/6.5 的证据链接）。

新增只读 `getTransportScope({"transports":["DEVK900001"]})`：读取显式传输成员；任务会展开到整个父请求及兄弟任务。
返回 `boundaryScope` 可用于图边界分析，但须先检查 `collection.status/issues`，并提供另行采集的结构依赖图；
仅有 `IN_TRANSPORT` 成员边不能证明没有外部依赖。LIMU 未映射、截断和读取失败均明确标记 partial，
不代表 CR 自动分组或传输可释放。详见[传输成员离线对齐](evidence/transport-scope-offline-alignment.md)。

### 6.1 离线依赖图分析（本地开发新增，尚未发布）

`analyzeDependencyGraph` 在 `focused` / `developer`、`operations`、`expert` 入口可用
（兼容 `development`、`diagnostic-readonly`）；`safe`、`business` 不开放。
此工具只分析传入的快照，不读取 SAP，也不验证来源标签。

```json
{
  "operation": "impact",
  "root": "CLAS:ZLIB",
  "graph": {
    "nodes": [
      { "id": "CLAS:ZLIB", "type": "CLAS", "name": "ZLIB" },
      { "id": "PROG:ZCALLER", "type": "PROG", "name": "ZCALLER" }
    ],
    "edges": [
      { "from": "PROG:ZCALLER", "to": "CLAS:ZLIB", "kind": "CALLS", "source": "PARSER" }
    ]
  },
  "maxDepth": 3,
  "edgeKinds": ["CALLS", "REFERENCES"]
}
```

边从「依赖者」指向「被依赖者」；上述请求返回 `ZCALLER`，深度为 1。
`operation: "stats"` 只传 `graph`，返回对象/边/包/来源统计。
节点上限 500、边上限 2000，实际容量同时受全局请求字节上限约束；
结果截断会显式标记。`completeWithinSnapshot` **不表示 SAP 全系统完整**，
空影响面不证明线上无影响。`LOADS` 不是调用；共同传输也不证明代码依赖。

无需 SAP 的进程级验证：构建后运行 `npm run test:dependency-graph:offline`。
该 smoke 使用虚拟目标、禁止网络连接，验证新进程、离线 healthcheck 与旧的
合成内存计划失效；不代表你的真实 MCP 客户端已经重启或部署完成。
详细范围见 [`依赖图离线对齐记录`](evidence/dependency-graph-offline-alignment.md)。

### 6.2 有界加载依赖图（已真机验证）

`buildLoadDependencyGraph` 将现有 D010INC 只读查询串行组合为多跳图。
部署后调用本工具**会读取 SAP**；于 2026-09-25 在专用 DEV 真机验证
（组合链单点读回 26 条 LOADS 边，见 [`结构边界真机验证`](evidence/transport-crossref-real-dev-verified.md)
与 [`传输范围真机验证`](evidence/transport-scope-real-dev-verified.md)）。

```json
{
  "objectType": "CLAS",
  "objectName": "ZCL_EXAMPLE",
  "direction": "loaded_by",
  "maxDepth": 2,
  "maxQueries": 5
}
```

- 默认 `loaded_by`：查谁加载它，返回图与快照影响面；`loads`：查它加载什么，只返回图与统计。
- 必须查看 `collection.issues` 和 `unexpanded`；达到深度/查询/容量上限、读取失败与截断都显式返回。
- FUGR 不支持反向展开；遇到此类节点会停止该节点并标注，不静默当作“无影响”。
- 图可再交给 `analyzeDependencyGraph`，但仅覆盖编译期 LOADS，不是完整调用图。
- `systemWideComplete=false`；未查根对象是否存在；顺序读取不是原子快照。

范围及离线证据见 [`加载依赖图接线记录`](evidence/load-dependency-graph-offline-alignment.md)。

### 6.3 传输/CR 对象集合边界（离线分析器 + 真机组合链）

`analyzeDependencyGraph` 的 `boundaries` 子操作检查给定集合的对外依赖；不读取或修改传输。
传入同一格式的 `graph`，以及显式对象集合：

```json
{
  "operation": "boundaries",
  "graph": {
    "nodes": [
      { "id": "CLAS:ZORDER", "name": "ZORDER", "type": "CLAS" },
      { "id": "INTF:ZLOGGER", "name": "ZLOGGER", "type": "INTF" }
    ],
    "edges": [
      { "from": "CLAS:ZORDER", "to": "INTF:ZLOGGER", "kind": "REFERENCES", "source": "PARSER" }
    ]
  },
  "boundaryScope": { "label": "CR-EXAMPLE", "objectIds": ["CLAS:ZORDER"] },
  "maxEntries": 200
}
```

示例会将 `ZLOGGER` 列为集合外的自定义依赖。**这不意味着 SAP 中没有它，
也不意味着必须加入该传输**：目标系统可能已有对应对象。
label 只是显示名称，不触发传输/CR 内容查询；CR 多传输并集需明确给出成员。
只按完整 TYPE:NAME 匹配，不把同名不同类型当作同一对象。

结果另外区分标准对象候选、命名空间归属不明、动态引用（`DYNAMIC_CALL`）、
跨包与包信息未知；不提供“可以安全释放”的判定。明细会按共享 maxEntries 预算截断，
summary 仍统计全部输入依赖。完整边界见
[`传输边界离线记录`](evidence/transport-boundaries-offline-alignment.md)。

### 6.4 传输结构边界组合链（真机验证）

`getTransportScope` 的 crossref/双源模式随下一 npm 版本发布（源码运行已可用）。它是"传输成员 → 结构依赖 → 边界分类"的一站式只读组合：

```json
{
  "transports": ["DEVK900010"],
  "includeCrossRefBoundaries": true,
  "maxDependencyQueries": 6,
  "maxEntries": 100
}
```

- 成员采集：任务编号自动展开为父请求与兄弟任务，返回 R3TR 成员并集（不含 LIMU）。
- `includeCrossRefBoundaries`：对每个代码承载成员（CLAS/INTF/PROG/FUGR）读
  WBCROSSGT/CROSS 出向边（REFERENCES/CALLS 口径）；INDIRECT 行是类型引用噪声被丢弃，
  PERFORM 行按所属程序归属，组件级引用（方法/表单）合并为对象级边。
- `includeLoadBoundaries`（默认行为兼容）：改为采集 D010INC 编译期加载边（LOADS）。
  两个开关至少一个为 true，可同时开启（每成员 crossref 消耗 2 次查询、loads 1 次，
  共享 `maxDependencyQueries` 预算，默认 5、上限 10）。
- 真机正例：S4HK900012 组合链产出 `FUGR:ZMCP_TOOLS → UNKNOWN:S_ADMI_FCD（CALLS）`，
  目标非成员且非 Z/Y → 正确分类 standardCandidates。
- 恒等关系成立：`totalDependencies = inScope + missingCustom + unknownNamespace + dynamic + standardCandidates`；
  `deploymentReadinessVerified` 恒为 false——组合链不构成传输可释放结论。
- 成员为空或 partial（LIMU 未映射/预算截断/读取失败）时必须先看
  `collection.status/issues`，不要把"没查到"读成"没有依赖"。

### 6.5 函数模块测试数据目录（真机验证）

（数据源：EUFUNC 集群表，relid='FL'，只读 key 与元数据列）：

EXPORT 数据集群，需要 S/2 集群解码器（尚未实现，notes 恒带此声明）。
从未保存过测试数据的模块返回空目录，这是正常回答而非失败。

### 6.6 TVARVC 配置引用分析（真机验证）

`getWhereUsedConfig` 找出"代码里读取 TVARVC 变量"的对象，两段式：

```json
{ "variable": "ZMY_VAR", "grep": true, "maxGrep": 10 }
```

- 候选采集：WBCROSSGT OTYPE='TY'（OO 类池）+ CROSS TYPE='S'（过程化）按
  NAME='TVARVC' 配对；单源失败可生存（unsearched 记录），双源失败是硬错误
  而非"无读者"答案。
- 源码 grep 确认：每候选源码大小写不敏感 grep 变量名；confirmed=true 仅当
  grep 命中；grep 失败/跳过/预算外一律 unsearched，绝不借用 confirmed=false
  语义。grep 预算默认 10、上限 30（本项目源码 grep 为客户端正则串行读取，
  与 VSP 无界不同）。
- 注意：WBCROSSGT/CROSS 行在对象激活时生成——刚写入未激活的引用不会被读到。

smoke：`npm run test:where-used-config-real-dev`。证据见
[`where-used-config 真机验证`](evidence/where-used-config-real-dev-verified.md)。

### 6.7 调用片段示例（真机验证）

`getUsageExamples` 给出目标对象被怎么使用的具体调用片段：

```json
{
  "objectType": "CLAS",
  "objectName": "ZCL_API",
  "method": "GET_DATA",
  "maxExamples": 10
}
```

- 候选 callers 按目标类型选交叉表查询：FUNC→CROSS TYPE='F'；PROG→TYPE='R'
  （SUBMIT）；form 场景 TYPE='U'（PERFORM 行 NAME=form）；CLAS/INTF→
  WBCROSSGT+CROSS 双表 LIKE。
- 逐候选读 source/main 全文做六形态匹配：CALL_FUNCTION / METHOD_CALL
  （`=>`/`->`/`~`）/ CLASS_REFERENCE（NEW / TYPE REF TO / CREATE OBJECT）/
  SUBMIT / PERFORM form IN PROGRAM；未命中时字面名 GREP 兜底（MEDIUM 置信）。
  注释行跳过；片段带前后 3 行行号上下文。
- 排序：非测试类优先、高置信优先、具体形态优先；maxExamples 默认 10、上限 50。
- 源码读取失败/空源码记 unsearched，不计入 totalCallers（不把"读不了"当
  "没人调用"）。

smoke：`npm run test:usage-examples-real-dev`。证据见
[`usage-examples 真机验证`](evidence/usage-examples-real-dev-verified.md)。

## 7. 故障处理

- `PLAN_NOT_FOUND`、`PLAN_EXPIRED`、`PLAN_ALREADY_CONSUMED`：重新 preview。
- `SOURCE_DRIFT`：重新读取源码并 preview，不覆盖人工修改。
- `CONFIRMATION_UNSUPPORTED`：改用支持 MCP form 的客户端，或明确启用较弱的文字降级。
- `ROLLBACK_FAILED`、`UNLOCK_FAILED` 或未知远端结果：停止自动重试，人工检查 SAP 对象、锁、非活动版本和传输。
- npm 解析失败：确认使用带作用域的固定 `abap-ai-workbench-mcp@0.10.0`，不要使用不带作用域的上游包或 `@latest`。
